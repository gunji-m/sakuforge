# ADR 0005: 最初の招待で提供する範囲を決める

ADR は「何をどう決めたか、理由は何か」を1件ずつ残す短い決定記録です。設計書ではなく、判断の履歴です。

- Status: Accepted
- Date: 2026-11-01
- Related: [ADR 0001](0001-declaration-and-origin.md)、[ADR 0004](0004-vercel-nextjs-server-side.md)、
  #8、#9、#20、#21

## 背景

[ADR 0001](0001-declaration-and-origin.md) は宣言、6つの軸、価値の順番を決めましたが、最初の招待で
何を誰にどこまで出すかは1か所にまとまっていませんでした。[ADR 0004](0004-vercel-nextjs-server-side.md) で、
CSV をサーバー関数で検査・集計して結果を JSON で返し、結果をブラウザが保持する形に決めたので、
その上で最初の範囲を決めます。

tfdata-api の ADR 0006 は、要件定義書を別に作らないとしていました。この ADR もその方針に沿い、範囲の
判断を ADR に置きます。規則の中身は各文書を正本とし、ここではリンクだけにします。

本人は 2026-11-01 に、この範囲と、ドメイン規則の確認（#9）から持ち越した論点を決めました。

## 決定

### 流れ

1. 入力: 証券会社の国内現物保有 CSV（固定22列。[ドメイン規則](../domain-rules.md)の2節）。取り込みを
   手軽にする方法は #2 の結果で見直す
2. 検査: ブラウザが CSV をサーバー関数へ送り、関数が検査と集計をして結果を JSON で返す。CSV も結果も
   サーバーに保存しない（ADR 0004）
3. 出力: 検査結果（所見）と、簡単なダッシュボードに描く次の集計結果。JSON の形は #21
   - トータル資産額（評価額の合計）
   - 年間配当見込み総額
   - 17業種別の構成比
   - 33業種別の構成比
4. 保持: 結果の JSON はブラウザ側に保持する。時系列の比較（総資産の推移の棒グラフ等）は次の段階で、
   最初の範囲には含めない（#4）

### 年間配当見込み

- 定義は、行ごとの 保有株数 × 予想1株配当 の合計。税引前の額とする
- 合計は常に「下限」と「上限」の2値で持つ。予想1株配当が範囲（`下限 ~ 上限`）の行は下限と上限を
  それぞれに足し、単一値の行は両方に同じ額を足す。範囲の行が無ければ下限と上限は等しい
- 預り区分（NISA、旧NISA など）が違う同じ銘柄の行は、区別せずにそのまま合算する
- 合計に上限は置かない。入力の桁の制限（[ドメイン規則](../domain-rules.md)の3節）だけで守る

評価額は 保有株数 × 現在値 で計算し、CSV の評価額の列は使わないので、端数が証券会社の表示と違うことが
あります。

### #9 から持ち越したドメイン規則の論点

[ドメイン規則](../domain-rules.md)への反映は #9 で行います。

- **銘柄マスターに無い銘柄**（ETF、REIT など）: CSV を拒否しない。その銘柄は構成の「未分類」に入れ、
  所見 `stock_code_unknown` は warning とする（`valid` は true のまま）。tfdata-api 由来の今の規則では
  warning の規則が無く、未知コードがあると `valid` が false になるので、**tfdata-api と結果が異なる**
- **33業種別の構成比**: 17業種と同じ規則（評価額、分母、計算不可、丸め、合計の補正なし、並び）で足す
- **所見 code**: 16件を据え置く。固定 message の文言は #9 で見直す（本人が #9 の反映 PR で文言案を選ぶ）
- **上限値**（サイズ、行数、列数、所見、未知コード、検査時間）: 据え置く。ただしサイズなどは Vercel の
  関数の上限で見直す可能性がある（#20、[設計](../design.md)の5節）

### しないこと

アカウント、サーバーへの利用者データの保存、課金、自己登録、宣伝。

### 非機能

- 入力の上限: [ドメイン規則](../domain-rules.md)の1節
- 出さないもの（応答、ログ、エラー）: [入力を信用しない原則](../input-trust-principles.md)の3節
- 銘柄マスターの出典表示と扱い: [外部データとの約束](../external-data-policy.md)
- 配置: [ADR 0004](0004-vercel-nextjs-server-side.md)、[設計](../design.md)

### 未決

- 入力の形を手軽にする方法（#2 の結果待ち）
- 銘柄マスター JSON の利用範囲（#3 の結果待ち。ブラウザへは配らない）
- Vercel の関数で扱える CSV の大きさと時間（#20 の結果待ち）
- 結果 JSON のデータ構造（#21）とブラウザ側の履歴（#4 の結果待ち）
- 対応ブラウザ（本人が決める）

## 検討した他の案

- **`docs/requirements.md` を作る。** 要件定義書を別に作らない tfdata-api の方針と合わず、判断と規則の
  置き場所が増える。範囲は判断なので ADR に置く。採らない
- **ADR 0001 に節を足す。** ADR 0001 は宣言と出自の判断で、範囲は後から変わり得る。Accepted の ADR を
  書き換えるより、別の ADR にして見直しの履歴を残すほうが追いやすい。採らない

## この決定で起きること

**良い面**

- 最初の招待で何を出し、何を出さないかが1か所にまとまる
- 未決の箇所と、それを決める Issue が分かる

**負担になる面**

- #9 で、`docs/domain-rules.md` に年間配当見込み、未知の銘柄の扱い、33業種の規則を反映する作業が要る
- 未知の銘柄の扱いが tfdata-api と異なるので、結果を突き合わせるときに差として扱う必要がある

**この決定では解消しないこと**

- 上の「未決」の各項目

## 見直す条件

- #2、#3、#4、#20 の結果で範囲が変わるとき。この ADR を書き換えず、新しい ADR で置き換える
- 招待の範囲、提供の形、出力の項目を変えるとき
