# ADR 0004: Vercel と Next.js に置き、CSV の検査と集計はサーバー関数で行う

ADR は「何をどう決めたか、理由は何か」を1件ずつ残す短い決定記録です。設計書ではなく、判断の履歴です。

- Status: Accepted
- Date: 2026-11-01
- Related: [ADR 0001](0001-declaration-and-origin.md)、[ADR 0002](0002-public-repository.md)、
  ADR 0003（実装言語を TypeScript にする）、#10、#3、#4、#20、#21

## 背景

[ADR 0001](0001-declaration-and-origin.md) は、検証と集計を純粋な関数として書き、サーバーで動かすか
ブラウザで動かすかを配置の選択として後から決めるとしました。ADR 0003 で言語を TypeScript に決めたので、
その関数をどこで動かし、画面をどこに置くかを決めます。

利用者データを預からないこと（ADR 0001 の「預かり方」）と、1人で作り1人で運用し費用を小さくすること
（同「制約」）が、配置を選ぶ主な条件です。

本人は 2026-10-31 に配置を Vercel、フレームワークを Next.js（App Router）にすると決め、2026-11-01 に
CSV の検査と集計をサーバー関数で行い、結果を JSON で返す形にすると決めました。

## 決定

- **核を分ける**: CSV の検査と集計の純粋関数は、Next.js に依存しない TypeScript のパッケージに置く。
  Next.js のアプリはそれを import するだけにする
- **サーバー関数で検査する**: ブラウザは CSV をサーバー関数（saku-API）へ送る。関数は核で検査と集計を
  行い、結果を JSON で返す。CSV も結果も保存せず、ログにも内容を出さない
- **画面はブラウザで描く**: ダッシュボードは、返ってきた JSON から Next.js の画面が描く
- **結果はブラウザが持つ**: 次回以降の比較（時系列）のために、結果の JSON はブラウザ側に保持する。
  形式は #21、保存場所と比較は #4 で決める
- **銘柄マスターはサーバー側だけで使う**: 照合と集計に使う銘柄マスター JSON はサーバー関数の中で読み、
  ブラウザへ配らない
- **サーバー関数は2つ**: 招待の確認と、CSV の検査と集計
- **置き場所**: Vercel。関数のリージョンは東京 `hnd1`
- **Next.js の使い方を絞る**: メジャーバージョンを固定する。Server Actions と高度なキャッシュの機能は使わない

### 条件

- Vercel の Hobby プランは非商用の利用に限られる。招待制、無課金、宣伝なし（ADR 0001 の宣言と軸）を
  守る間だけ Hobby プランで置く
- Vercel の関数には、リクエスト本文の大きさ、実行時間、memory の上限がある。[ドメイン規則](../domain-rules.md)の
  入力上限をその中で満たせるかは #20 で確かめ、上限値は #9 で決める
- 銘柄マスター JSON をサーバー関数へどう置くか（配備物に含めるか、リポジトリ外から読むか）は、
  リポジトリに入れない（[ADR 0002](0002-public-repository.md)）ことを守って設計で決める。利用範囲は #3 で確認する

### 理由

- **預からない**: CSV は関数の処理の間だけ memory にあり、保存しない。利用者の端末に残るのは結果の JSON だけ
- **結果がそろう**: 上限と検査時間をサーバーの資源で測るので、利用者の端末の速さで結果が変わらない
- **銘柄マスターを配らない**: 照合をサーバーで行うので、銘柄マスターをブラウザへ渡さずに済み、
  再配布にならないよう保守的に扱える（[外部データとの約束](../external-data-policy.md)）
- **大きさ**: サーバー側は2つの関数だけで、VPS、OS、Web サーバーの運用が要らない
- **配置を後から選べる**: 核が Next.js に依存しないので、ブラウザ側へ移すときも核は書き換えない
- **費用**: 少数招待の範囲では Hobby プランで足りる見込み

Next.js は、画面と関数を同じアプリに置けるので採ります。Server Actions とキャッシュの機能は、どこで何が
動くかを1時間で説明しにくくするので使いません。

## 検討した他の案

- **ブラウザで検査と集計を行い、CSV をサーバーへ送らない。** CSV が端末の外へ出ない点は強いが、
  銘柄マスターをブラウザへ配る必要があり、検査時間の結果が端末に依る。採らない。ただし、Vercel の関数で
  CSV の大きさや時間を扱えないと分かったとき（#20）の保険の案として残す。核が Next.js に依存しないので、
  切り替えても核は書き換えない
- **Vite と React の静的サイトにし、API を Hono 等で別に置く。** 画面と API の配備が2つになる。
  Next.js の機能を絞れば大きさは抑えられるので採らない
- **VPS に自前で配備する。** tfdata-api の形で、OS、Web サーバー、TLS、監視を1人で運用する負担が大きい。
  利用者データを預からない後継では、その負担に見合う理由が無い。採らない

## この決定で起きること

**良い面**

- 検査の結果が端末に依らず、銘柄マスターをブラウザへ配らずに済む
- サーバーの運用がほぼ無くなる

**負担になる面**

- CSV が一度サーバーに届くので、保存しないこと、ログ・エラー・監視に内容を出さないことを、実装と
  Vercel の設定の両方で守る必要がある（[入力を信用しない原則](../input-trust-principles.md)の3節）
- Vercel の関数の上限に入力上限が縛られる（#20）
- Vercel と Next.js の変更に追従する手間がある。メジャーの固定で頻度を抑える

**この決定では解消しないこと**

- パッケージ構成と道具の選択（設計の文書と AGENTS.md）
- 招待の確認の具体（合言葉の扱い等）
- 結果 JSON のデータ構造（#21）とブラウザ側の履歴（#4）
- 銘柄マスター JSON の利用範囲（#3）

## 見直す条件

- Vercel の関数で、入力上限の CSV を受け取れない、または時間内に処理できないと分かったとき（#20）。
  ブラウザで検査する案に切り替えるかを決める
- Vercel の料金、Hobby プランの条件、リージョン、関数の上限などの条件が変わったとき
- 商用利用、課金、宣伝が要件になり、Hobby プランの条件を満たさなくなったとき
- Next.js のメジャー更新や機能の変化で、使い方を絞ったままでは保守できなくなったとき
