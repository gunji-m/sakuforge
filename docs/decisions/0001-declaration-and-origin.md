# ADR 0001: 宣言と出自を定め、tfdata-api から思想と規則だけを引き継ぐ

ADR は「何をどう決めたか、理由は何か」を1件ずつ残す短い決定記録です。設計書ではなく、判断の履歴です。

- Status: Accepted
- Date: 2026-10-31
- Origin: gunji-m/tfdata-api の [ADR 0006](https://github.com/gunji-m/tfdata-api/blob/4a25bc93e8dba5b8bce866d6707bce6415ec61da/docs/decisions/0006-small-invited-service-and-review-phase.md)（宣言と5つの軸）、
  [ADR 0007](https://github.com/gunji-m/tfdata-api/blob/4a25bc93e8dba5b8bce866d6707bce6415ec61da/docs/decisions/0007-no-user-data-at-rest-and-successor-repository.md)（利用者データを預からない形と後継リポジトリ）
- Related: [ADR 0002](0002-public-repository.md)

## 背景

sakuforge は gunji-m/tfdata-api の後継です。tfdata-api の ADR 0007 で、利用者データを預からない形へ移り、
コードと Git 履歴は持ち込まず、思想、ドメインの規則、作り方の規則だけを持って新しいリポジトリで作り直すと
決めました。同じ ADR が、2つのリポジトリを後継の ADR 0001 に置く「出自」の1文でつなぐとしています。

この ADR は、その出自の1文と、引き継いだ宣言・軸・価値を、このリポジトリの最初の判断として固定します。

## 決定

### 出自

> 出自は gunji-m/tfdata-api の main `4a25bc93e8dba5b8bce866d6707bce6415ec61da`。判断の履歴はそちら。

### 宣言

> 開発者以外の少数の利用者に、招待で使ってもらう。品質と安全を優先し、公開しても問題を
> 起こさないサービスにする。宣伝はしない。開発者自身が内部を理解できる大きさに保つ。
> 利用者データを預からない。

tfdata-api の ADR 0006 の宣言に、ADR 0007 の「利用者データを預からない」を足したものです。この宣言を、
すべての要件の一番上に置きます。

### 6つの軸

ADR 0006 の5つの軸をそのまま引き継ぎ、「預かり方」を6つ目の軸として足します。

| 軸 | 決めたこと |
| --- | --- |
| 目的 | 他者が使うサービスにする。学習は副次目的。判断が割れたら「学びが多いほう」ではなく「問題を起こしにくいほう」を選ぶ |
| 利用者 | 顔の見える少数を招待する。自分で登録できる仕組み、SNS などでの宣伝、不特定多数向けの公開は当面行わない |
| 価値 | 「普段はサッと、気になったら深く、日本株の資産を理解できる」 |
| 制約 | 1人で作り、1人で運用する。費用は小さく。他人の金融資産データと、取引所から得たデータを扱う |
| 大きさ | 開発者が1時間で全体を説明できる大きさに保つ。説明できない部分は削るか、別のものに置き換える |
| 預かり方 | 利用者データを預からない。CSV を受け取って検査・集計の結果を返すだけで、保有明細、取込履歴、メールアドレスを保存しない。履歴の比較はブラウザ側に持つ |

### 価値の順番

1. まず CSV の取り込みと構成（17業種）の確認
2. 次に取り込み時点同士の比較（ブラウザ側の履歴。#4）

### 最初の招待で提供する範囲

2026-10-31 に #8 で追記しました。要件定義書は別に作らず（tfdata-api の ADR 0006 と同じ方針）、何を誰に
どこまで出すかの判断をここに置きます。規則の中身は各文書を正本とし、ここではリンクだけにします。

**流れ**

1. 入力: 証券会社の国内現物保有 CSV（固定22列。[ドメイン規則](../domain-rules.md)の2節）。取り込みを
   手軽にする方法は #2 の結果で見直す
2. 検査: 利用者のブラウザで検査と集計を行い、CSV をサーバーへ送らない（ADR 0004）
3. 出力: 検査結果（所見）、17業種の構成、年間配当見込み
4. 履歴: 取り込み時点同士の比較はブラウザ側に持つ次の段階で、最初の範囲には含めない（#4）

**年間配当見込み**（本人の方針、2026-10-31）

- 最初の範囲に含める
- 定義は、行ごとの 保有株数 × 予想1株配当 の合計。予想1株配当が範囲（`下限 ~ 上限`）の行があれば、
  合計も下限と上限の2値で示す
- 上限は一旦1千万円とする
- 計算規則の正本は[ドメイン規則](../domain-rules.md)に置く（#9 で反映する）

**#9 から持ち越したドメイン規則の論点**（[ドメイン規則](../domain-rules.md)への反映は #9）

- 銘柄マスターに無い銘柄（ETF・REIT など）: CSV を拒否せず、その銘柄を構成の「未分類」に入れ、所見
  `stock_code_unknown` を warning として残す。tfdata-api 由来の今の規則では warning の規則が無く、
  未知コードがあると検査結果が valid にならないので、**tfdata-api と結果が異なる**
- 所見 code 16件と固定 message: 据え置く
- 上限値（サイズ、行数、列数、所見、未知コード、検査時間）: 値を据え置く。ブラウザ側で動かすと意味が
  変わる点は[設計](../design.md)の5節を参照

**しないこと**

アカウント、サーバーへの利用者データの保存、課金、自己登録、宣伝。

**非機能**

- 入力の上限: [ドメイン規則](../domain-rules.md)の1節
- 出さないもの（応答、ログ、エラー）: [入力を信用しない原則](../input-trust-principles.md)の3節
- 銘柄マスターの出典表示と扱い: [外部データとの約束](../external-data-policy.md)
- 配置: ADR 0004、[設計](../design.md)

**未決**

- 入力の形を手軽にする方法（#2 の結果待ち）
- 銘柄マスター JSON の配布境界（#3 の結果待ち）
- ブラウザ側の履歴（#4 の結果待ち）
- 対応ブラウザ（本人が決める）

### 作り方

- 検証と集計を純粋な関数（入力だけから結果が決まり、保存や通信をしない関数）として1言語で書く。
  サーバーで動かすかブラウザで動かすかは、その関数の配置の違いとして後から変えられるようにする
- 言語は ADR 0003 以降で決める。この ADR では決めない

### tfdata-api から引き継いだもの

ADR 0007「3. 引き継ぐもの」の7層を、次の文書に置きます。

| 層 | このリポジトリでの置き場所 |
| --- | --- |
| 目的と利用者の宣言 | この ADR |
| 価値 | この ADR |
| ドメインの規則（保有 CSV の22列、数値の字句規則、証券コード、配当の範囲表記、17業種の構成計算、検査所見） | [ドメイン規則](../domain-rules.md) |
| 入力を信用しない姿勢 | [入力を信用しない原則](../input-trust-principles.md) |
| 外部データとの約束 | [外部データとの約束](../external-data-policy.md) |
| 作り方の規則（1 Issue／1 branch／1 PR、Merge commit、進行 Issue、ラベル体系、template、AGENTS.md の骨格、検証の報告） | [Git workflow](../git-workflow.md)、[AGENTS.md](../../AGENTS.md)、`.github/` |
| 判断の残し方（ADR の書式） | `docs/decisions/` |

テストの合成 CSV fixture と期待値は、言語が決まった後に新しい言語のテストとして書き直します。tfdata-api の
Python 実装は、後継の実装と結果を突き合わせる参照にだけ使い、持ち込みません。

### tfdata-api に置いてきたもの

サーバーで利用者データを預かる時代の判断は持ち込みません。

- VPS、SSH トンネル、loopback Nginx を前提にした信頼境界（tfdata-api ADR 0003・0004）
- JWT 認証と所有者条件、利用者データの永続化、MySQL と Alembic
- バックアップと保持・削除の設計
- CI の配備前確認と image 診断、本人1名前提の運用手順
- 銘柄マスターの DB 同期。後継では月1回、手元で JSON を生成して読む

詳細と理由は tfdata-api の ADR 0007「3. 引き継ぐもの」「4. 置いていくもの」を正本とします。

## 検討した他の案

- **ADR 0006 の5つの軸だけを引き継ぎ、「預からない」は宣言の文だけに書く。** 預からないことは、後の
  設計判断（保存先、ログ、ブラウザ側の履歴）を最も強く縛る条件で、軸として表に置いたほうが判定に使いやすい。採らない
- **出自の1文を README だけに書く。** ADR 0007 が後継の ADR 0001 に置くと決めているので、それに従う

## この決定で起きること

**良い面**

- 宣言と軸が1か所にあり、下位の文書や Issue が宣言に沿っているかを判定できる
- 出自の1文で、tfdata-api の判断の履歴へたどれる

**負担になる面**

- コードが無い状態から始めるので、言語の決定と検証関数の実装が先に必要になる
- 判断の履歴が2つのリポジトリに分かれる

**この決定では解消しないこと**

- 言語の選定（ADR 0003 以降）
- 銘柄マスター JSON の配布境界（#3）
- LICENSE（本人が選ぶ。[ADR 0002](0002-public-repository.md)）

## 見直す条件

- 端末をまたいだ履歴の共有などのために、利用者データをサーバーに保存する必要が出たとき
- 招待制から利用者が自分で登録できる形へ広げるとき、商用利用や課金が要件になったとき
- 1時間で全体を説明できる大きさを保てなくなったとき
