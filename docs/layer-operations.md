# α層・β層の運用

α層（作戦）とβ層（オーケストレーション）が読む、Issue運用と開発体制の手続き。実装層は読まなくてよい。人間の承認が必要な範囲は [`AGENTS.md`](../AGENTS.md) にある。

## Issue運用

正本は agent-workflows の `templates/github/issue-operations.md`（同期日：2026-11-08）。ここには要点とこのリポジトリの補足だけを書く。

- 作業の入口はIssue。テンプレートは進行・開発・検証・タスクの4種類（`.github/ISSUE_TEMPLATE/`）。
- 種類ラベルを1つ（進行管理／開発／検証／タスク）。Openの作業Issueには状態ラベルを1つまで（次の作業／作業中／データ待ち／ユーザー確認待ち／保留）。進行Issueには状態を付けない。未採用の仮説は「検討候補」。
- タイトルに種類の印を付けない。状態を変えるときは本文の現在地も一緒に直す。
- 分けるときは「進行 → 開発／検証 → タスク」。小さな変更は分けない。子1件の完了で親を閉じない。
- 全体の入口（段階の一覧、ピン留め）の下に、段階ごとの進行Issueを置く。段階の進行Issueは開発・検証Issue数件〜10件ほど、開発Issueは1つの成果（PR 1〜3本ほど）を目安にする。決めるIssueと作るIssueを分け、前提の判断が済んでから起票する。
- 完了したらClosedにして状態ラベルを外し、種類ラベルは残す。

### このリポジトリの補足

- `.github/` のテンプレートは写し。変えるときは先に正本を変える。
- branch、PR、merge、完了の正本は [`docs/git-workflow.md`](git-workflow.md)。
- 「データ待ち」は、毎月の東証の上場銘柄一覧のファイルなど、外部データを待つときに使う。
- Issue に個人を特定できる情報を書かない。貼るのは合成データだけにする。

## 開発体制

正本は agent-workflows の `templates/development-layers.md`（同期日：2026-11-08）。ここには要点とこのリポジトリの補足だけを書く。

- α層（作戦）が Issue を起票し、β層（オーケストレーション）が拾って実装層に指示し、成果を確かめて PR にする。報告は PR・Issue コメントと進行Issueの現在地に残す。
- β層は「次の作業」が付いた開発・検証 Issue だけを拾い、着手したら「作業中」にする。
- 定型の作業は実装層の軽い設定、設計判断を含む実装は強い設定に渡す。
- 実装層への再依頼が 1 Issue（複数の PR に分けたときは 1 PR）で 3 回を超えたら、「ユーザー確認待ち」を付けて止まる。設計判断が必要なときも「ユーザー確認待ち」でα層に差し戻す。理由と再開条件は現在地に書く。
- 確認なしで進めてよい範囲だけを触る PR は、CI が通り、レビューの指摘・未解決のスレッド・競合が無く、PR 本文の「決めてほしいこと」が「なし」なら、β層が merge する。人間の承認が必要な範囲（`AGENTS.md`）に触れる PR は、開発者の指示を待つ。
- 開発者からの直接の依頼にも同じルールを当てる。

### このリポジトリの補足

- 確認なしで進めてよい範囲：Issue の完了条件の中での `packages/core` の実装とテスト、合成データによるテスト、規則を変えない文書の修正、Issue の状態とコメントの更新
- branch、PR、merge の規則は [`docs/git-workflow.md`](git-workflow.md) にある。
